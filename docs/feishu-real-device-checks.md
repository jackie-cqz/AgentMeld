# 真机验证清单（需要人在飞书里操作）

三件**无法从代码、日志或自动化测试里得到答案**的事。它们都依赖飞书客户端的实际行为与真实账号配置，所以只能由人在真群里做一次并记录结果。

每项都写了：**怎么做 → 看什么 → 结论填哪里 → 不同结果意味着什么**。做不完也没关系：**没有做过的项必须在文档里保持「未验证」**，不能因为代码看起来对就写成已验证。

前置条件：

- 一个真实群（当前测试群 `oc_1ac9122165a8dbc27ab38cf3c572f11b`），以及**两台设备**（或一台电脑 + 手机）。
- 至少两个真实应用已绑定：`cli_aa45114061789c1b`（Conductor）、`cli_aa4512cf2bb8dc0a`（PM 小灰）。
- 能看到 `pnpm dev` 的控制台输出（日志里搜 `[feishu]`）。
- 一个**不是绑定者**的账号也在群里（这是检查 A 与 C 的关键：绑定者自己的点击看不出可见性差异）。

## A. 卡片回调的可见范围（toast / 卡片更新给谁看）

**为什么必须真机**：我们回给卡片动作的 `toast`（例如「已回答。」「只有绑定这个应用的账号可以回答。」）与卡片**就地更新**，在飞书里是「只有点击者可见」还是「全群可见」，代码里看不到——平台决定。

**步骤**

1. 在群里 @ 一个 Bot，让它问一个问题（`ask_user`，单选即可），卡片出现。
2. **绑定者**点其中一个选项，观察**点击者自己的屏幕**：是否出现 toast？卡片是否就地变成「已选择」？另一问的按钮是否仍然可点？
3. 立刻问**群里那个非绑定账号**（或看你的第二台设备，用**另一个账号**登录）：
   - 他**看得到 toast 吗**？
   - 他屏幕上的**卡片内容变了吗**（是否也显示「已选择：…」与「已由 张三 回答」）？
4. 让非绑定账号点一次按钮，观察他自己看到的提示（预期：只有他能看到「只有绑定这个应用的账号可以回答。」这类的 toast，群里其他人看不到）。

**看什么 / 记录**

| 观测点 | 结果（填：仅点击者 / 全群 / 看不到） |
|---|---|
| 成功 toast「已回答。」 | |
| 拒绝 toast「只有绑定这个应用的账号可以回答。」 | |
| 卡片就地更新（已选择 + answeredBy） | |

**不同结果意味着什么**

- **toast 仅点击者可见**：那么「回答已记录」的反馈是**个人化**的——群成员不会因为别人回答过而看到提示。卡片更新才是全群可见的载体，这也是为什么卡片在回答后仍然保留按钮（inert），而不是变成一句纯文本。
- **toast 全群可见**：那拒绝提示会**在群里刷屏**（每个非绑定账号点一次就一条）。若真如此，应把拒绝路径从 toast 改成仅更新卡片/静默，避免噪音——这是一条**新的产品决策**，需要单独开 PR。
- **卡片更新仅点击者可见**：那我们的「应答即改卡」在群里等于没发生，需要改成先回消息再更新（同样要单独开 PR）。

## B. 同一应用两条连接时，事件是否被瓜分

**为什么必须真机**：§3 的隐患是「同一 appId 两条 WS 长连接 → 平台把事件分给其中一条，另一条收不到 → 消息丢一半」。代码层面我们做了 appId 索引 + 重连前断开（#58），但**平台到底怎么分发，只有在真连接上才看得到**。

**步骤**

1. 正常启动一个实例（`pnpm dev`），确认日志里该应用是 `connected`。
2. **制造第二条连接**，任选一种：
   - 在**另一个目录/另一个进程**里用同一个 `appId`/`appSecret` 启动第二个实例（例如另开一个终端跑 `pnpm start`）；或
   - 让第一个实例正在连接时立刻再启动一次（竞态）。
3. 在群里连续发 **10 条**不同的 @ 消息（内容带序号 `#1`…`#10`），每条之间隔 2 秒。
4. 在两个实例的日志里分别数：各自收到几条 `[feishu]` 入站、各自的 `messageId` 列表。
5. 停止第二个实例，再发 5 条，确认第一个实例全部收到。

**看什么 / 记录**

| 观测点 | 结果（填：10/10、5/5 分给两条、某条为 0、其它） |
|---|---|
| 实例 A 收到的条数 | |
| 实例 B 收到的条数 | |
| 两条之和是否等于 10 | |
| 停掉 B 后 A 是否 5/5 | |

**不同结果意味着什么**

- **两条之和 = 10 且各自不重复**：平台**按连接轮询/瓜分**，§3 的隐患**成立**。那么「一个应用只允许一条连接」必须成为**硬约束**：`startFeishuChannels` 已经在做同进程内去重，但**跨进程**（两个 `pnpm dev`）无法互相阻止——需要在启动时加一个基于 appId 的**文件锁/单实例守卫**，并把它做成独立 PR。
- **两条都各收到 10 条（重复投递）**：平台广播给所有连接，隐患**不成立**，但同一消息会被两个实例各处理一次（靠 `(channel, external_message_id)` 唯一键在**共享同一个 SQLite** 时去重；两个进程各用各的库则会重复回答）。此时要在文档里写明「多实例必须共用同一个数据目录」。
- **只有一条收到、另一条为 0**：平台**固定选一条**，隐患降低为「另一条是死连接」；`disconnectFeishuApp` + 重连前的关闭（#58）已覆盖主要场景，记录即可。

## C. `boundByOpenId` 与回调 `operator.openId` 是否同一命名空间

**为什么必须真机**：授权判定是 `回调 operator.openId === 绑定记录 boundByOpenId`。两者都叫「openId」，但在飞书里 openId **按应用维度**取值——同一个人的 openId 在每个应用下都不同。绑定记录来自**注册时**的返回，回调来自**点击时**的平台事件，如果其中一个取自**别的应用**或**别的 id 类型**（user_id / union_id），授权会**全量拒绝**（fail-closed，表现为「只有绑定这个应用的账号可以回答」）。

**步骤**

1. 找出绑定记录：在数据目录里查 `channel_bindings` 的 `bound_by_open_id` 与 `bot_open_id`（或看启动日志）。
2. 在群里点一次按钮（用**绑定时用的那个飞书账号**），从日志里取出该次回调的 `operator.openId`。
3. 比对两者**字符串是否完全相等**；再与**另一个应用**的绑定记录比一比（同一个人的 openId 应当**不同**）。
4. 用一个**没有绑定过**的账号点一次，确认被拒（这是反向验证：如果它也通过了，说明授权根本没生效）。

**看什么 / 记录**

| 观测点 | 结果 |
|---|---|
| 应用 A：`bound_by_open_id` vs 回调 `operator.openId`（相等？） | |
| 应用 A 的 `bot_open_id` | |
| 应用 B：同一个人的 `bound_by_open_id`（与 A 不同？） | |
| 未绑定账号点击是否被拒 | |

**不同结果意味着什么**

- **相等、且跨应用不同、未绑定被拒**：授权模型成立，可以删掉 §6.3 里「未在真机验证」的措辞。
- **不相等但本人能作答**：说明回调里的 openId 是**另一套 id**（可能取决于应用配置的 id 类型），必须把授权改成用**同一来源**的值比较；这是**安全相关**的修正，要立刻开 PR。
- **未绑定账号也能作答**：授权失效，属于必须立刻修的漏洞（先把 `boundByOpenId` 为 null 时的 fail-closed 路径再确认一遍）。
