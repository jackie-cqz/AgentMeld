# 飞书渠道运维说明

这份文档讲**怎么跑、怎么判断它在工作、坏了怎么查**。设计决策与理由在
[agentmeld-feishu-channel-design.md](./agentmeld-feishu-channel-design.md)，这里不重复。

**一条贯穿全文的规则**：本文只写**实测过**的事实。凡是推测或未验证的，都明确标出来。
这个项目已经有过三次「从文档推导出结论、当成事实写下来、后来被证伪」的记录
（一键清单的 scope、产物入口「不可能」、路径守卫「与文件浏览器同一条」），
所以这里对未经实测的说法一律加「未验证」或「推断」。

## 1. 绑定

一个 Agent 绑一个飞书**自建应用**，走扫码（OAuth 设备授权）。绑定关系存在
`channel_bindings`。**App Secret 是明文存储的**（`app_secret` 列，没有加密），
这与项目里其他凭据（各家模型的 API Key）一样；它不会经任何接口返回，只有连接层会读它。
谁能读到 SQLite 文件，谁就拿到了这些应用的完整权限（见 §7）。

- **二维码有效期**：会话跟随 SDK 实际返回值，实测 `expireIn = 3600` 秒。
  公开文档写「十分钟」，**不要用文档的数字**。
- **一个 Agent 一个 Bot 身份**是刻意设计：群里谁说话就是谁说话。**不要**塌缩成
  「一个 Conductor Bot + 网页投影」。
- **换绑不是覆盖，是删了重来**。已绑定的 Agent 再发起绑定会得到 **409**；
  唯一路径是先解绑（删除绑定行、断开连接）再扫码。**每一次成功扫码都会创建一个
  全新的飞书应用**（`createOnly: true`，防止复用别人的应用）——旧应用在飞书侧
  **不会被删除**（没有删除 API，设计风险 R4），成为孤儿。频繁换绑 = 攒孤儿应用。
- `boundByOpenId` 取自注册返回值。它为 `null` 时授权全部拒绝（见 §6.3），
  修复路径同样是解绑重扫（也就意味着一个新孤儿应用）。

## 2. 一键清单到底给了什么（实测）

这是**最容易出错、也最值得先读**的一节。一键创建应用预填的权限清单
**不等于**你可能需要的权限。

| 能力 | 实测结果 |
|---|---|
| 收「@ 了 Bot」的群消息 | ✅ 可用（`im:message.group_at_msg:readonly` 等） |
| 发消息 / 发卡片 | ✅ 可用（含不带长连接的发送，见设计文档 §8.1.6） |
| **上传并发送文件** | ✅ **可用**（`POST /im/v1/files` 返回 200 + `file_key`；SDK 的 `send(chat, { file })` 全路径成功） |
| 建长连接收事件 | ✅ 可用，**无需公网地址** |
| **列出群内机器人**（`getChatBots`） | ❌ **400**（实测）。清单里没有服务端要求的那四个 scope 中的任何一个 |
| **列出群成员**（`getChatMembers`） | ❌ **推断，未实测**。按 scope 清单推断同样缺权限；只实测过 `getChatBots` 是 400 |
| **读回群内所有消息** | ❌ **推断，未实测**。一键清单里没有 `im:message.group_msg`，据此推断读不回（含 App 自己发的消息）；没有实测过任何「读回」类接口 |

**两个直接后果**：

1. **按名字 @ 别人不可靠**。名册来源不可用，只能用**已知 openId** 构造提及。
   两种失败写法都是**静默失效**——写错了不会报错，只是没人被 @ 到。
2. **「让 Bot 读群里的全部消息」这条路默认不存在，而且不需要**：网页由 AgentMeld
   自己的状态喂，本来就是完整记录；群是投影。

> 想加权限：`addons` 可**增量**追加，**不能**删减基础权限；敏感配置（事件订阅方式、
> 回调地址、加密 key）**不能**经 `addons` 传，要走 `application-config` OpenAPI。

## 3. 一条应用 = 一条长连接

「平台会把一个应用的事件分散到两条同时存在的长连接上」是**飞书官方文档的说法，
本项目没有实测复现过**（设计文档 §8.2 第 5 条记为未验证）。但防御照做：
连接层按 **appId**（不是 agentId）建索引，**注册表不会登记同一应用的两条连接**。
注意这**不等于**「不可能存在两条活连接」——重连路径不保证先断开旧 channel（§8
「重连可能残留旧连接」），那一条说的是实况。

> ### ⚠️ 给排障的人
> **不要在 dev server 正在跑的时候，用同一个应用另开一条 WS 探针。**
> 如果官方说法属实，那会把事件分流，你会看到"有些消息收不到"，并花很长时间怀疑代码。
>
> 需要探针时：**只调 HTTP API，不要 `connect()`**。本文提到的文件发送探针就是这样做的。
> 它验证了 `send()` 不需要 WS，所以这条路是安全的。

## 4. 怎么判断它在工作

### 4.1 看日志

```bash
# Agent 的回答发到了哪个群（带 message id）
grep "\[feishu\] projected"

# 运行失败的公告（带 message id）
grep "\[feishu\] announced failure"

# 提问卡 / 审批卡（各一条，带 message id）
grep "\[feishu\] asked"

# 产物投递（带字节数）
grep "\[feishu\] delivered"

# 被跳过的投递，以及原因
grep "\[feishu\] not delivering"
```

日志不是唯一的观测面：**投递健康度接口**（§4.4）回答「最近有没有失败」，
**入站消息表**回答「消息进来没有」（见下）。

**每个 [feishu] 成功日志对应什么**：`projected` = Agent 回答；`announced failure` =
失败公告；`asked a question` / `asked for approval` = 提问卡与审批卡。
**进展卡没有成功日志**——它只有失败日志（`failed to post run progress` /
`failed to settle run progress` / `failed to refresh a run card`，最后一条随 #46 增加）。
「进展卡发出没有」要从群里看，或从投递健康度接口侧面看。

> ⚠️ **入站没有成功日志，但不是不可观测。** 路由**只在出错时**打日志
> （`[feishu] failed to route an inbound message`）；正常路径一条日志都不打。
> 但每条路由成功的入站消息都会落库（`channel_inbound_messages` 表），
> 所以「消息进来没有」查表可得。真正的观测缺口是**静默丢弃**：
> 不 @ Bot 的消息、Bot 自己的消息——这些连表里都没有。

### 4.2 看接口

| 接口 | 用途 |
|---|---|
| `GET /api/channels/feishu/bindings` | 绑了哪些 Agent |
| `GET /api/channels/feishu/connections` | 每条连接的状态、bot 名字、失败原因 |
| `GET\|POST /api/channels/feishu/projection` | **全局暂停开关**：停掉出站发送 |
| `GET /api/channels/feishu/delivery` | **投递健康度**：每个「会话 + Agent」发送成功/失败的次数、最后一次错误和时间（局限见 §4.4） |

**暂停开关是全局的**，覆盖**所有主动发送**：消息、失败公告、产物、提问卡、审批卡、
进展卡，以及这些卡片事后的结算改写。
**它管不到卡片按钮的回调响应**——点击后经 SDK 回调返回的 toast 和（提问/审批卡的）
就地改写不走发送通道，暂停时照常工作。这是刻意的（点击总要有点击的反馈），但排障时要知道。
**例外**：进展卡的「查看状态」按钮（#46）刷新时走 `updateCard`＝主动发送——暂停时
它的 toast 照常，但卡片改写被抑制，且计入投递健康度（见 §4.4）。

### 4.3 一次健康的往返长什么样

出站一侧：

```
[feishu] projected ag_pm -> oc_xxxxx (om_xxxxx)
```

入站一侧没有日志（见 §4.1），查 `channel_inbound_messages` 表；或最直接：
看群里有没有出现回答。

### 4.4 投递健康度能回答什么、不能回答什么

`GET /api/channels/feishu/delivery` 返回每个「会话 + Agent」的：`sent`、`failed`、
`lastError`、`lastFailureAt`、`lastSuccessAt`。**所有主动发送（消息、卡片、卡片更新、
文件、失败公告、限速提示）都经过同一个包装器计数**，失败记录后会重新抛出，调用方各自决定怎么处理。

**它回答得了的**：某个会话最近有没有发送失败、错误是什么。

**它回答不了的（读之前先知道）**：

- **只统计「真的走到了发送」的尝试。** 没有连接（channel 为空）、暂停、
  已经投影过的消息——**这些不产生行**。限速**提示本身**会经过包装器，所以
  Agent 回答触发限速时**会产生行**；但产物与进展卡被限速跳过时**只跳不发**，
  不产生行。所以 `{"delivery": []}` **不等于一切正常**，也可能是「根本没有尝试过」。
  要区分，对照 `connections` 接口看连接状态。
- **进程内存里的记录，重启即清空。** 重启后它回到 `[]`。
- **`sent` 把消息和卡片更新混在一个桶里。** `sent: 50, failed: 0` 可能是 50 次卡片更新、0 条消息。
- **`lastError` 在之后成功时不会被清掉，也没有「最后一次尝试」的时间。**
  一次早已恢复的失败读起来像持续故障；对照 `lastFailureAt` 与 `lastSuccessAt` 才能判断。
- **错误被截断到 300 个字符，这不是脱敏。** 前 300 个字符里如果有敏感内容，它照样在响应里，
  而这个接口和其余接口一样**没有鉴权**（见 §7）。
- **卡片按钮的回调响应不计数**——toast 与提问/审批卡的回传卡片不是发送。
  例外：「查看状态」按钮的卡片改写是主动发送（`updateCard`），**计入健康度**、受暂停抑制。

## 5. 失败模式

| 现象 | 含义 |
|---|---|
| 群里完全没反应，网页有 `⚠️ Workspace not found.` | 渠道会话没有工作区。**已修**：该通知现在会带 Agent 身份并发进群 |
| 群里没反应，网页也没有 | Agent 没绑应用，或连接失败了 → 查 `connections` |
| 「本会话短时间内的消息过多…」 | 触及限速（每会话 20 条/分钟，滚动窗口）。**当轮被跳过的消息不会补发** |
| 卡片点了没反应 | 已结算的卡片会提示"已经处理过了"；跨群/非拥有者会被拒绝 |
| 消息只到了一半 | **如果** §3 的两连接分流属实（未验证），这是首要嫌疑；排除法：确认没有第二个进程在跑同一应用 |

## 6. 重启与状态

进程启动时 `instrumentation.ts` 依次拉起：入站路由 → 出站投影 → 交互（提问/审批）
→ 运行进展 → 产物投递。**每进程各一份订阅**，重复启动是幂等的。

**进行中的 run**：重启后由 `run-recovery` 直接置为失败。恢复流程**不发任何事件**，
所以重启前发出的卡片**不会被回收**——按卡片类型分三种下场：

- **提问卡 / 审批卡**：待答项只在内存里，重启即消失。卡片留在群里，
  点击会提示「已经处理过了」。**不是「重新点一下就能继续」**——待答项本身没了，
  运行已被标记失败，**只能重新发起任务**。
- **部分已收集的答案**：同样只在内存里，与待答项一起丢失。
- **进展卡**：卡片注册表也在内存里。重启后群里的进展卡**永远显示「进行中」**，
  取消按钮点击会得到「这次运行已经结束了」的提示，但卡片本身不会更新。

### 6.3 `boundByOpenId` 为 null

卡片作答/审批/取消的授权依赖 `boundByOpenId`。它为 `null` 时**拒绝所有人**（fail-closed）。
**没有事后补写的路径**，只能解除绑定后重新扫码（注意 §1：这会又建一个新应用）。

## 7. 安全边界（重要，别误解）

卡片上的「只有绑定人可以作答/批准/取消」**不是一层认证边界**。

- 它校验的是平台回调给的 `operator.openId` 与绑定记录的 `boundByOpenId` 是否一致。
- **`boundByOpenId` 来自注册返回值，回调的 `operator.openId` 来自回调**——
  两者是否同一命名空间，**只有部分证据**：消息事件的 `senderId` 与它同值（实测），
  **但卡片回调那条路径没有在真实点击中验证过**。若命名空间不同，生产上会**全部拒绝**，
  而所有测试仍是绿的。
- **App Secret 明文存放在本地数据库里。** 接口不会返回它，但**读到数据库文件的人**
  （本机其他进程、备份、误提交的 `.agentmeld-data/`）能直接拿到。配合下一条，风险叠加。
- **HTTP API 级完全没有鉴权**（issue #24）。任何能访问端口的人都能读写一切。
- **没有发送者白名单**：任何能 @ 到 Bot 的人（包括 `/deploy` 这类触发词路径）都能启动运行，
  同样属于 #24 要收的口子。

## 8. 已知缺口

| 缺口 | 说明 |
|---|---|
| **部署预览** | 需要群成员能打开的**公网地址**，与「本地优先」矛盾，未解。**产物文件不需要地址，已实现**，两者不要混为一谈 |
| **状态查询** | **已实现（随 PR #46 合入）**：进展卡上的「查看状态」按钮。不引入飞书特有语法，每次改写卡带版本号绕开 SDK 的点击去重 |
| **`code_file` / `diff` 产物投递** | `code_file` 有分支但**本仓库没有生产者**（`write-artifact` 只接受 `web_app\|document\|image\|ppt`）；`diff` **连投递分支都没有**，走通用失败理由。生产上都走不到 |
| **`web_app` 产物** | **已实现**：单页且资源可内联 → 发一个自包含 `.html`；否则 → 发 `.zip`（不丢文件）。两者都不需要公网地址。**未验证**：`.html`/`.zip` 在飞书客户端/移动端的呈现方式没有真机确认（§4.4 同类未验证项） |
| **`ppt` 产物** | **已实现**：渲染成一个自包含的 HTML 幻灯片（无外部引用、可打印成 PDF）。**不是 .pptx**——手写 OOXML 意味着要自带 slide master/layout/theme 且无法诚实验证，打不开的 pptx 比一定能打开的 HTML 更糟。**未验证**：飞书客户端的呈现方式 |
| **网页侧产物同步** | **已实现**：`POST /api/artifacts`、`PATCH /api/artifacts/:id`、`POST /api/artifacts/:id/versions` 都会发 `artifact.create`，群里因此能看到网页上创建/编辑的产物。网页新建的产物**没有作者**，投递时从**这个群里观测到的成员**中挑一个有活连接的 Bot 代发（有作者的产物仍用作者；候选依次尝试，投递失败会换下一个；**代价**：如果平台其实已经收下、但响应丢失/超时导致调用方看到失败，下一个 Bot 会再投一次，群里可能出现两份同样的文件（这个取舍换掉的是「第一个候选恰好不在群里就整份丢失」）。PATCH 与 versions 都是**新建一行**（新 id、version+1），所以每次有效编辑都会投递一份新文件——刻意如此；**无改动的更新（PATCH 与 versions 都是）不会新建行也不会投递**。
| **产物删除不通告** | 网页删除产物（`DELETE /api/artifacts/:id`）**不发事件**，群里已投出去的文件不会撤回，也没有任何提示。需要时再单独做一个「撤回/更新」消息 |
| **并发编辑会产生重复版本** | `createNewArtifactVersion` 是「读-改-插」且无事务：并发两次编辑同一产物会得到**两行同为 version+1**、各自投递一次。既有竞态，本轮只记录 |
| **话题隔离** | **已实现**：入站消息的话题 id 落库（`channel_inbound_messages.thread_id`），Agent 的回答通过 SDK 的 `reply` **回到提问所在的话题**（非话题里的提问仍发到群里顶层）。未验证：飞书话题在客户端里的实际呈现（与 §4.4 其它未验证项同类）。代价：reply 结果不确定时（超时/unknown，SDK 内部已处理 `target_revoked`）会回落到顶层，可能因此出现两份。注意只有**直接回答**回到话题：产物文件、进展卡、失败通报，以及 **conductor 派发的子任务回答**（子 run 的触发消息是 conductor 造的、从不入站，因此找不到话题）都发顶层 |
| **群成员只增不减** | **已实现但当前不生效**：本 Bot 被拉进群（`botAdded`）时记录自己并**对账**该群成员——用 `getChatBots({force:true})` 拉群内 Bot，把已不在群里的观测成员移除。**但它依赖 `getChatBots`，而本表记录该接口实测返回 `400`（一键清单缺 `im:chat:readonly` 等服务端要求的 scope）**，所以今天的生产部署里对账只会打一行 `could not list the chat's bots` 然后什么都不改——机制正确、**能力未就位**。授予该 scope 后即生效。另外：飞书**有**「机器人被移出群」事件 `im.chat.member.bot.deleted_v1`（一键清单里的 `im:chat.members:bot_access`），但本 SDK 只包装了进群事件；直接订阅它更直接，尚未实现。限制：只删**我们持有其 bot id** 的成员（认不出的一律保留）、只清成员证据表，不动会话 `agentIds` |
| **群成员只增不减** | **已实现但当前不生效**：本 Bot 被拉进群（`botAdded`）时记录自己并**对账**该群成员——用 `getChatBots({force:true})` 拉群内 Bot，把已不在群里的观测成员移除。**但它依赖 `getChatBots`，而本文档「一键权限清单」一节记录该接口实测返回 `400`（一键清单缺 `im:chat:readonly` 等服务端要求的 scope）**，所以今天的生产部署里对账只会打一行 `could not list the chat's bots` 然后什么都不改——机制正确、**能力未就位**；授予该 scope 后即生效。飞书**有**「机器人被移出群」事件 `im.chat.member.bot.deleted_v1`（scope `im:chat.members:bot_access` 已在一键清单里），但本 SDK 只包装了进群事件；直接订阅它是更直接的路线，尚未实现。限制：只删**我们持有其 bot id** 的成员（认不出的保留）、只清成员证据表，不动会话 `agentIds` |
| **`multiSelect` 提问** | 卡片上退化成单选（网页用 `"; "` 连接多选） |
| **并发点击** | 不存在「两个人抢答」：只有绑定应用的账号能作答，别人在任何缓冲被查到之前就被拒绝。可达的只有**拥有者从两台设备点**，以最后一次为准，且第二台设备拿回的卡片显示的就是最终值（见 `interaction.ts` 里的注释和对应测试） |
| **限速记账不完整** | 限速（`recordSend`）现在覆盖 Agent 回答、产物、**进展卡首次发送**；但进展卡的**就地改写**（结算、以及每次点「查看状态」触发的刷新）既不查也不记账——连点状态按钮可以无限触发改写。另外 `withinSendBudget` + `recordSend` 与其它出站一样是**先查后记**，多个 run 并发启动时同一窗口内可能略超上限。
| **重连可能残留旧连接** | **已修**：重连前先关闭旧 channel（失败则本轮不重连，避免第二条 socket）。副作用：重连窗口内（最长 20 秒连接超时）该应用会短暂从状态列表消失，出站被跳过——方向安全但不是无声的。
| **回调响应的可见范围** | 点按钮后回传的卡片/toast 是只有点击者可见还是全群可见，**未在真机验证** |

## 9. 环路防护（六层，现状）

| 层 | 状态 |
|---|---|
| 1 入站永不产生出站（架构） | ✅ |
| 2 投影白名单（只发 Agent 的回答、失败与系统通知） | ✅ |
| 3 来源闸门（Bot 的消息不启动任何运行） | ✅，有验收测试 |
| 4 每会话限速（20 条/分钟） | ✅，**记账覆盖 Agent 回答与产物**（进展卡查而不记，见 §8） |
| 5 合并/卡片就地更新 | 部分：进展卡与卡片都就地更新，消息不合并 |
| 6 `botLoopGuard`（`onTrip: "reject"`） | ✅，**测试覆盖到装配与转换**：策略配置传入（enabled + onTrip）有断言；合成 `reject` 事件 → `rejected:bot_loop` 连接事件的转换有测试。**LoopGuard 本身（阈值/窗口，SDK 内部）与「真实 ping 触发」路径没有本地测试** |

**第 6 层没测过什么**要说准确：本地测试证明的是「策略按要求装配了」和「拒绝事件
能变成可见的连接状态」；**从未证明过** LoopGuard 会在真实环路里触发（那需要平台
发来真的 ping/自环消息）。真实环路本来就被第 1 层从架构上排除，第 6 层是兜底，
而兜底的触发条件本身未经本地验证——知道这一点再信它。
